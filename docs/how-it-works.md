# Как работает rate-limiter

## Что такое rate limiting

Это ограничение «не больше N запросов за время T» для одного клиента. Нужно, чтобы:

- один клиент (или бот) не положил сервис для всех остальных;
- нельзя было перебирать пароли тысячами в секунду;
- платные API могли продавать тарифы «1000 запросов в час».

Клиента определяет «ключ»: IP-адрес, id пользователя, API-ключ — что угодно, что вернёт функция `keyFunc`.

## Общий интерфейс

Оба алгоритма реализуют один интерфейс (`limiter.go`):

```go
type Limiter interface {
	Allow(ctx context.Context, key string) (Result, error)
}
```

На вопрос «можно ли этому ключу сделать запрос?» он отвечает: да или нет, сколько запросов ещё осталось и, если нельзя, через сколько можно будет. Благодаря интерфейсу middleware и сервис не знают, какой алгоритм внутри, — его можно поменять одной строкой.

## Алгоритм 1: Token bucket (ведро с жетонами)

Файл `token_bucket.go`.

Представим у каждого клиента ведро, в которое помещается `limit` жетонов. Каждый запрос забирает один жетон. Если ведро пустое — запрос отклоняется. При этом ведро постоянно понемногу пополняется: при лимите 60 в минуту — по одному жетону в секунду.

```
ведро на 3 жетона, +1 жетон в секунду

t=0.0  ●●●  запрос → ●●○  ✓
t=0.1  ●●○  запрос → ●○○  ✓
t=0.2  ●○○  запрос → ○○○  ✓
t=0.3  ○○○  запрос → ✗  (следующий жетон через 0.7 с)
t=1.0  ●○○  запрос → ○○○  ✓
```

Хитрость реализации: никакой таймер жетоны на самом деле не добавляет. Мы храним для ключа только два числа — сколько было жетонов и когда мы последний раз смотрели. При следующем запросе считаем, сколько времени прошло, и досыпаем жетоны «задним числом»:

```go
elapsed := now.Sub(b.updatedAt).Seconds()
b.tokens = math.Min(float64(tb.limit), b.tokens+elapsed*tb.perSec)
```

`math.Min` не даёт ведру переполниться: если клиент молчал час, у него будет не тысяча жетонов, а ровно `limit`.

Жетоны — дробные (`float64`): через полсекунды у клиента может быть 0.5 жетона. Из этого же считается, сколько ждать: не хватает `1 - tokens` жетона, скорость пополнения известна, делим одно на другое.

**Плюсы:** очень быстро (всё в памяти, никакой сети), разрешает короткие всплески до размера ведра, но в среднем держит скорость.

**Минусы:** живёт внутри одного процесса. Если запущено три копии сервиса за балансировщиком, у каждой своё ведро, и клиент на деле получит лимит ×3.

### Почему нужен mutex

`Allow` вызывается из разных горутин одновременно — каждый HTTP-запрос в Go обрабатывается в своей горутине. Без `sync.Mutex` две горутины могут одновременно прочитать «остался 1 жетон», обе его «забрать», и пройдут два запроса вместо одного. А ещё запись в `map` из нескольких горутин без блокировки — это гонка данных, которая может уронить программу. Тест `TestTokenBucketConcurrentRequests` запускает 200 горутин на лимит 50 и проверяет, что прошло ровно 50; тесты гоняются с `-race`, который ловит такие ошибки.

## Алгоритм 2: Sliding window log (скользящее окно) в Redis

Файл `sliding_window.go`.

Чтобы лимит был общий для всех копий сервиса, состояние должно лежать где-то снаружи. Тут это Redis.

Идея простая: для каждого ключа храним время каждого запроса за последнее окно. Новый запрос разрешён, если в окне меньше `limit` записей.

```
окно 60 секунд, лимит 3, сейчас 12:01:10

запросы в 12:00:05, 12:00:40, 12:00:55, 12:01:05
           ↑ уже вне окна (старше 12:00:10) — выкидываем
в окне остаются 3 → новый запрос ✗
ждать до 12:01:40, когда уйдёт запрос 12:00:40
```

В Redis для этого есть sorted set — множество, где у каждого элемента есть число (score), и по нему можно быстро выбирать и удалять диапазоны. Score — время запроса в микросекундах.

На каждый запрос выполняется четыре команды:

1. `ZREMRANGEBYSCORE` — удалить всё, что старше начала окна;
2. `ZADD` — добавить текущий запрос;
3. `ZCARD` — посчитать, сколько запросов в окне;
4. `PEXPIRE` — поставить ключу срок жизни, чтобы Redis сам удалил данные клиента, который перестал ходить.

Они отправляются через `TxPipelined`, то есть в `MULTI/EXEC`: Redis выполнит их подряд, не вклиниваясь командами других клиентов, и за один сетевой запрос.

Если после добавления записей стало больше лимита — запрос отклоняется, и мы удаляем свою запись обратно (`ZREM`). Иначе отклонённые запросы тоже занимали бы место в окне, и клиент, который долбит без остановки, никогда бы не дождался разблокировки. Это проверяет `TestSlidingWindowRejectedRequestsAreNotCounted`.

Время ожидания считаем по самой старой записи: она уйдёт из окна через `её время + окно - сейчас`.

У каждого элемента множества должно быть уникальное имя, иначе два запроса в одну наносекунду схлопнутся в один. Поэтому имя — время плюс случайное число.

**Плюсы:** точно (никаких «примерно»), общий лимит для любого количества копий сервиса.

**Минусы:** на каждый запрос — поход в Redis, и в Redis хранится по записи на каждый запрос (при лимите 10 000 в час это 10 000 записей на клиента).

## Middleware

Файл `middleware.go`. Обычная для Go обёртка: функция принимает `http.Handler` и возвращает новый, который сначала спрашивает лимитер, а потом либо зовёт исходный, либо отвечает `429 Too Many Requests`.

В ответ всегда добавляются заголовки `X-RateLimit-Limit` и `X-RateLimit-Remaining`, а при отказе — `Retry-After` в секундах (округляем вверх, чтобы клиент не пришёл на долю секунды раньше и снова не получил отказ).

**Что делать, если Redis упал?** Тут два варианта: не пускать никого (fail closed) или пускать всех (fail open). Я выбрал fail open: лимит — это защита, а не основная функция, и из-за упавшего Redis не должен лечь весь сервис. Ошибка пишется в лог. Для чего-то вроде защиты логина от перебора правильнее было бы наоборот.

## Тесты и время

Проверять «через 30 секунд лимит восстановится» с настоящим `time.Sleep` — долго и нестабильно. Поэтому у лимитеров есть поле `now func() time.Time`. В коде там `time.Now`, а в тестах подставляется `fakeClock`, который двигается вперёд только когда скажешь `clock.Advance(30 * time.Second)`. Все тесты проходят за доли секунды.

Redis в тестах заменяет miniredis — это реализация Redis на Go, которая запускается прямо внутри теста. Docker не нужен, и можно заглянуть внутрь: проверить, сколько записей лежит в множестве и какой у ключа TTL.
